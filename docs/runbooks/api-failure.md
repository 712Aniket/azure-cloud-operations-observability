# Runbook: API Failure Investigation and Recovery

## 1. Purpose

This runbook describes how to investigate and respond to HTTP 5xx server errors generated by the Azure Cloud Resume Challenge Function App.

It covers alert detection, Application Insights investigation, troubleshooting, recovery and incident closure.

## 2. Monitored Resources

| Setting | Value |
|---|---|
| Azure Subscription | Azure subscription 1 |
| Resource Group | rg-portfolio |
| Azure Region | centralindia |
| Function App | aniket-portfolio-api |

| Action Group | ag-portfolio-failures |

## 3. Alert Detection

Azure Monitor uses a scheduled query alert to detect HTTP 5xx server errors.

### Alert KQL Query

```kusto
requests
| where toint(resultCode) >= 500
| where timestamp > ago(5m)
```

### Alert Configuration

| Configuration | Value |
|---|---|
| Evaluation Frequency | 5 minutes |
| Evaluation Window | 5 minutes |
| Time Aggregation | Count |
| Operator | GreaterThan |
| Threshold | 0 |
| Minimum Failing Periods | 1 |
| Evaluation Periods | 1 |
| Severity | 2 - Warning |
| Action Group | ag-portfolio-failures |

When the query detects matching failed requests, Azure Monitor triggers the alert and the Action Group sends an email notification.

## 4. Incident Response Procedure

### Step 1: Review the Alert

When an API failure notification arrives:

1. Sign in to Azure Portal.
2. Navigate to Azure Monitor.
3. Open Alerts.
4. Locate `alert-portfolio-api-failures`.
5. Review the alert firing time.
6. Identify the affected resource.
7. Check the alert details and number of failed requests.

### Step 2: Investigate Failed Requests

Navigate to:

Application Insights → aniket-portfolio-api → Logs.

Execute the following KQL query:

```kusto
requests
| where toint(resultCode) >= 500
| where timestamp > ago(1h)
| project timestamp, name, url, resultCode, duration, operation_Id
| order by timestamp desc
```

Review the following information:

- Timestamp of the failure.
- Request name and URL.
- HTTP response code.
- Request duration.
- Operation ID.

The operation ID can help correlate a failed request with related telemetry.

### Step 3: Investigate Application Exceptions

Execute:

```kusto
exceptions
| where timestamp > ago(1h)
| project timestamp, type, outerMessage, operation_Id
| order by timestamp desc
```

Investigate:

- Exception type.
- Exception message.
- Timestamp.
- Associated operation ID.

Use this information to identify potential application-level problems.

### Step 4: Investigate Failed Dependencies

Execute:

```kusto
dependencies
| where timestamp > ago(1h)
| where success == false
| project timestamp, name, target, resultCode, duration, operation_Id
| order by timestamp desc
```

Investigate whether external dependencies are contributing to the failure.

For this project, particular attention should be given to:

- Azure Cosmos DB connectivity.
- Database access and permissions.
- External service availability.
- Dependency response times.

### Step 5: Review Overall Request Distribution

Execute:

```kusto
requests
| where timestamp > ago(1h)
| summarize TotalRequests = count() by resultCode
| order by TotalRequests desc
```

This query provides a summary of requests grouped by HTTP response code.

Use it to understand the overall request success and failure distribution.

## 5. Common Failure Scenarios

| Symptom | Possible Investigation |
|---|---|
| HTTP 500 | Investigate application exceptions and Function App logs. |
| HTTP 502 | Investigate application availability and upstream service responses. |
| HTTP 503 | Check hosting availability and service health. |
| Cosmos DB errors | Investigate database connectivity, permissions and configuration. |
| Authentication errors | Review identity configuration and access permissions. |
| Slow API responses | Investigate request duration and dependency performance. |
| Repeated failures | Determine whether the issue affects a specific endpoint or the entire API. |

These are possible investigation areas and should not be treated as confirmed root causes.

## 6. Recovery Procedure

After identifying the underlying issue:

1. Review application logs and relevant telemetry.
2. Identify the affected component.
3. Correct the application, configuration or dependency issue.
4. Follow the approved deployment process when application changes are required.
5. Verify the Function App health endpoint:

   `https://aniket-portfolio-api.azurewebsites.net/api/health`

6. Confirm that the health endpoint returns HTTP 200.
7. Verify that the visitor counter API is working correctly.
8. Check Application Insights for new failed requests.
9. Confirm that the Azure Monitor alert returns to a resolved state.
10. Document the root cause and corrective action.

Do not make unreviewed production changes.

## 8. Security and Operational Precautions

- Never expose passwords, API keys or connection strings in application logs.
- Never commit credentials, private keys or Terraform state files to GitHub.
- Use secure authentication and access mechanisms.
- Do not disable monitoring alerts to hide failures.
- Avoid unnecessary testing against production visitor data.
- Use the approved GitHub Actions deployment workflow.
- Preserve Terraform remote state in Azure Storage.
- Review Terraform plans before applying infrastructure changes.
- Ensure temporary test endpoints are removed after testing.

## 9. Incident Closure Criteria

An API failure incident can be considered resolved when:

- The underlying issue has been identified and addressed.
- The health endpoint returns HTTP 200.
- The visitor counter API works correctly.
- Application Insights shows normal request behaviour.
- No new unexpected HTTP 5xx errors are observed.
- The Azure Monitor alert returns to a resolved state.
- The incident and corrective actions are documented.
